# Image pins and baked tools

Read before touching `docker/Dockerfile` pins, `docker/compose.yaml` images, or anything the image bakes.

**Baked image**: tools like `esbuild` and `bun` arrive via `docker/install-sidecars.sh` (takes component args — `esbuild`); Cello and Caddy are `ARG`s in `docker/Dockerfile`, pinned exactly once (`check-versions.ts`). Adding a new binary requires an **image rebuild**, and a `bun add`-less dependency edit requires a manual `bun install` to refresh the lockfile. Do not bump these pins casually.

## Updating a pin

Nothing is pinned by a tag or a version alone: base images are `image:tag@sha256:…` and every download carries its per-arch checksum (amd64 _and_ arm64). For a base image, take the multi-arch index digest (`docker buildx imagetools inspect <image:tag> --format '{{.Manifest.Digest}}'`), keep the tag, and update `<NAME>_DIGEST` in `docker/Dockerfile` (`docker/compose.yaml` and the `rustfs` service in `.github/workflows/ci.yml` for the store). For a download, take the publisher's checksum — Node's signed `SHASUMS256.txt` (its `.sig` verifies against `nodejs/release-keys`), the per-arch `@esbuild/*` package's `dist.integrity` (sha512, hex), the GitHub release asset's `digest`, or rustup's own `rustup-init.sha256` — and bump the version and both arch checksums together. Then run `bun docker/check-versions.ts --online --online-images`: `--online` compares every tarball/registry pin with the publisher's file (Node's signed `SHASUMS256.txt`, the `@esbuild/*` `dist.integrity`, rustup's `rustup-init.sha256`, jup/npm/pnpm integrity) and fails a bump that left a stale digest; `--online-images` adds the image tag digests. Image tags are not immutable — official images re-push the same tag for a base-OS update (rust's `1-bookworm`, bun's `1.4`, even `node:24.22.3-slim`), so `check.yml` resolves them only for a PR that changes a pin and the weekly `pin-drift.yml` run does it otherwise, keeping one `Image pin drift` issue open while a tag moved. Release builds and the merge queue deliberately skip the image leg: Docker pulls the pinned digest, so a re-pushed tag cannot change what ships; the weekly job is what notices it. A moved tag is not a build failure to ignore: take the new digest deliberately and rebuild. Build both platforms before pushing (the `image` job also does) so an arch-specific pin cannot pass unnoticed.
