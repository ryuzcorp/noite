# End-to-end lanes

Detail for the container lanes. The rule in `AGENTS.md` holds: e2e coverage comes from CI, and local runs are for reproducing a failure.

## Lanes

- E2E: `make e2e` — boots the prod image in its own compose project (`-p noite-e2e`): control UI through Caddy on :8090, runner API/git :8080, tenants 20000+, rustfs :19000 (`E2E_RUSTFS_PORT`); then runs doctor + Playwright (passkey signup, git push, deploy, tenant serve). Builds the image from the tree by default; `TAG=<short-sha> make e2e` pulls that release from GHCR instead. `make e2e-isolation` is the same lane in `NOITE_TENANCY=multi` plus the hostile-tenant spec (`E2E_HOSTILE=1`). Two suites over the same specs: `E2E_SUITE=fast` runs the tagged PR gate (`@fast` on single, `@isolation` on multi, plus the setup/policy projects) plus every spec file the PR rewrote in full (a changed shared helper escalates to `release` instead), and the default `release` runs every spec. Tagging is opt-in: a new test joins `release`, and joining the `fast` gate is a decision. On PRs, `ci.yml` runs `fast` automatically when runtime code changes (`apps/**`, `packages/**`, `docker/**`, `Makefile`, `bun.lock`, `.env.example`, `e2e.yml`) and `release` on the `e2e` label; `E2E_SPECS="e2e/a.spec.ts …"` narrows either suite to files. `E2E_KEEP=1` leaves the stack up for debugging (the slot stays held until `E2E_SLOT=<n> make e2e-down`). Always fresh: the lane removes its own project's containers and volumes (by label and name) and uses its own `noite-e2e` bucket. Stop the prod/dev stack first (same host ports). Parallel lanes: `E2E_SLOT=<n>` (or `auto` for the first free lock) gives each lane its own compose project, names, bucket and port block — slot 0 is exactly today's lane. The script takes the slot's own lock itself (`/tmp/noite-e2e-lane-<slot>.lock`, bounded wait via `E2E_LOCK_WAIT`), so a lane never runs unlocked and no outer `flock` wrapper is needed. Never hold a slot more than 30 min, never touch a stack you didn't start, and prefer CI for full runs. CI builds the image once per run (`ci.yml` `image` job) and each lane loads it; each lane shards its suite across the plan's cells (usually 2 jobs, `E2E_SHARD`, reports `playwright-report-{lane}-r{round}-s{shard}`; 1 job where a split would strand a shard empty); the nightly schedule runs 3 rounds per lane and files `flake` issues.

## Isolation coverage

**Isolation coverage comes from CI**, not a pre-PR local run: touching `host/exec.rs`, `deploy.rs`, `netisolation.rs`, `isolation.rs`, `db/alloc.rs` (uid allocation) or the Dockerfile puts the PR's multi lane on the `@isolation` specs (hostile, fleet-oom, domains, deploy), and the merge queue runs the full `release` suite on both lanes before anything lands. A local `make e2e-isolation` runs that whole suite, so keep it for reproducing a failure — narrowed, e.g. `E2E_SPECS=<spec> make e2e-isolation`.
