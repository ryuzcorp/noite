# Merging and review flow

Mechanics behind the merging rules in `AGENTS.md`. Read before opening a PR.

- **One push per review round.** Each push restarts CI (~5 min) and strips `security-reviewed`, so collect every finding first (CodeRabbit threads, security review, CI), fix them all, then push once. CodeRabbit reviews a PR once, when it is marked ready, and doesn't re-review on later pushes; ask for a second pass with `@coderabbitai review`, and only after a substantial change.
- **Order:** CI green and every CodeRabbit thread answered or resolved → independent security review and `security-reviewed` (when the gate asks for it) → merge queue. Never start the security review against a red or still-moving PR.
- **CodeRabbit is advisory.** Do not wait for it: the free tier regularly stops at "Review limit reached". If CI is green and the security review is in, merge; a valid finding that lands afterward is a roadmap candidate — unless it is release-blocking: a security, isolation or data-integrity defect is fixed before it ships (if the PR already merged, as a stop-the-line follow-up in the same loop).
- Open PRs as drafts; mark ready only when the report is written — the ready toggle is the PR's one CodeRabbit review. Merge only on green: `main` requires the `ci-ok` and `security-gate` checks, and merges through a squash merge queue.
- **~800 changed lines per PR**, excluding lockfiles, generated bindings (`apps/noite/src/lib/runner-types/`) and `changelog.d/` fragments. A bigger item is split: dependent layers go up as a GitHub stack (`gh stack init|add|submit|sync|rebase|merge`; every PR in a stack is still evaluated against `main`), independent items as parallel PRs.
- Local e2e is for reproducing a failure, not for pre-flighting a PR: on a runtime-code change PR CI runs the fast suite on both lanes (`@fast` on single, `@isolation` on multi, plus the PR's rewritten specs in full) in ~5 min, and the merge queue follows with the full `release` suite on both lanes before anything lands. The `e2e` label upgrades the next PR run to that `release` suite — labels never start CI by themselves, so push (an empty commit if the branch is otherwise done), close/reopen, or dispatch after labeling. Don't run the full lanes locally before opening a PR; bring the stack up only to reproduce a failure, narrowed (`E2E_SPECS="e2e/prs.spec.ts" make e2e`). The one local run CI cannot replace is a release-image smoke test (`TAG=<short-sha> make e2e`), which belongs to cutting a release.
- If a push starts no `pull_request` run at all within two minutes, that is GitHub's (see the note in `ci.yml`; nothing in this repo filters or skips it): close/reopen the PR, or `gh workflow run ci.yml --ref <branch> -f suite=release`.
- In the queue, `merge_group` runs never skip by paths and never cancel each other or a PR's run.
- `.github/security-paths.yml` lists change-sensitive paths (auth, isolation, secrets, the image, the gates themselves). Touching one fails `security-gate` until a reviewer, never the change's author, reads the diff and adds the `security-reviewed` label. Every push strips it again, a rebase included. After a pure rebase or a stack retarget, the reviewer relabels once `git range-diff <old-base>..<old-head> <new-base>..<new-head>` shows no change in the PR's own commits. A retarget onto a different base also needs that base's new content reviewed. Labelling does not re-run CI.

## Stacks

A dependent item over the size cap goes up as a GitHub stack (`gh stack init|add|submit|sync|rebase|merge`; one layer per concern, each green and reviewed on its own), then merges atomically with `gh stack merge <stack> --yes`: it queues all layers together, so no retarget re-strips labels. Never stack unrelated items: one failing layer blocks everything above it.
