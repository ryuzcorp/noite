Registration is by invitation once the instance is bootstrapped. The **first** account bootstraps it, and on a public base it must prove it is the operator: with `NOITE_ADMIN_EMAIL` set, only that address may register first and it must still present the one-time setup code printed at boot (knowing the address alone never suffices — it is promoted to the `admin` role on success); without it, the first registration must present the code alone (see [Install](/self-hosting/install)). On a `localhost`-family base the first account needs no proof and just becomes admin. Every later account arrives one of two ways: an admin invites its address, and it registers through the one-time link — or, with the registration waitlist enabled, it registers uninvited and waits for an admin to approve it.

Setup codes are 20 characters in four-char groups (`ABCD-EFGH-JKLM-NPQR-STUV`) drawn from an unambiguous alphabet (2^100 codes); only the SHA-256 hash is stored, a code works once, and the claim spends it atomically with the admin grant, so one code admits exactly one account even under concurrent signups. A lost code is reissued on the server (`docker compose exec noite noite-runner setup-code` — the old code dies). Invitation links carry a single-use token (128 bits, URL-safe): only the SHA-256 hash is stored, each link is bound to one invited address and expires after 7 days, and the token is shown to the admin once, at creation. Registration has no mailbox proof, so the address alone never grants access — the token is the proof. A token that is used, revoked, expired, unknown, or presented with a different address is refused with a specific message before any account is created. Redemption is a single atomic claim, so one link admits exactly one account even under concurrent signups.

- Admins invite an address from the Users tab of the admin home (the control app's detail page at `/apps/_control`): the one-time link is shown once for copying, and emailed when delivery is configured. Outstanding invitations are listed there with revoke.
- With the registration waitlist on (Settings tab, off by default), an uninvited registration creates a `pending` account that holds no access until an admin approves it on the Users tab; approval optionally emails the new account. With the waitlist off, uninvited registration is refused and leaves no account behind.
- The signup form shows the setup-code field on a fresh public install (in both modes — the reserved address must still present the code). Past the first account it accepts an optional invitation token: an invite link (`/login?invite=…`) pre-attaches it, and the server decides — invited or (with the waitlist on) queued, otherwise refused.

`NOITE_ADMIN_EMAIL` reserves the first account by address — which must still present the setup code — and promotes the matching account to the admin role at startup; it is documented in [Environment variables](/reference/environment-variables).

## First-run onboarding

A new account sees a one-time three-step tour the first time it reaches the dashboard: create an app and push to its Git remote, mint an API token (keys live on the Account tab of the Noite app — `/apps/_control?t=account` — used as the Git HTTPS password with username `git`, or as `NOITE_API_KEY` for the CLI), and where to follow the project. Finishing, skipping, or closing the modal marks the account done (`user.onboardedAt`) and it never returns. An account that signed in before this release sees the tour once and is then marked the same way; no operator action is needed.

## Lost passkey

On the login screen, **Lost passkey?** emails a six-digit code (valid 10 minutes, five attempts) and, once entered, signs the account in on the page where you add a new passkey. Emailing needs `NOITE_EMAIL_WEBHOOK_URL`: the control UI POSTs `{ "email", "otp", "from", "type": "sign-in" }` to it, and whatever you point it at (a mail relay, an automation) delivers it. Without a webhook nothing is sent on a real domain: the control UI logs the failure, and the screen still says a code was sent. Use the command below.

An operator who cannot wait for email, or never set a webhook, mints the same code on the server:

```bash
cd /opt/noite
docker compose exec noite noite-runner recover                   # for the instance owner (oldest admin)
docker compose exec noite noite-runner recover --email me@example.com
```

It prints a code and where to enter it. The code is the same kind the email carries: it works once, expires after 10 minutes, and anyone holding it can sign in as that account, so treat the output like a password. Running it needs a shell in the container, which already holds every secret of the install, so it grants nothing that access did not.

## The admin home

Every signed-in account sees the control plane itself in `/apps`: the **Noite** card, which is not a user app but a link to a dedicated detail page. For an instance admin that page is the whole admin home — the control plane's telemetry tabs (Overview, Metrics, Errors, Logs) next to instance administration (Users, Apps) and the instance switches (**Settings**: anonymous telemetry, release check, the registration waitlist), with the control database linked from Overview. Any other account sees only its own **Account** tab there: profile, passkeys, API keys and agent connect. Every admin tab re-checks the same rule server-side: a real instance admin, never an impersonated session.

**Ban** in the Users tab revokes the account's sessions and deletes its API keys, so `git push`, event ingest and `/mcp` stop immediately. The ban is checked on every request as well, so a key that somehow survived the deletion is still refused. Unbanning does not restore a deleted key: the account mints a new one.

Pending accounts show with a badge plus **Approve** and **Reject**. Approving flips the account active (an approval notice is emailed when delivery is configured); rejecting deletes the account, its passkeys and its sessions. A pending account holds no access until approval: no page data, no API calls, no key use. Pending rows can never be made admin before approval, and an admin cannot approve or reject their own account.

In `make dev` the control UI runs under vite and supervises no celld, so Metrics, Errors and Logs are hidden — there is no control fleet to record them — while the Users and Apps tabs and the control database still work.

## Browsing the control database

The Overview tab lists the control database; it opens on its own page (`/storage/_control/d1:noite-control`) in the same D1 grid tenant apps use, served **in-process** from the control node's own database — the worker already owns that binding, so nothing shells out to the `celld d1` CLI (which once hung every later page load; see SPEC.md). Each row also links to the proper admin action: a `user` row and an `email_invite` row both offer **Manage in Users**, pre-filling the tab's search with the row's email.

The browser is deliberately narrow:

- Values that would leak credentials are masked and never leave the worker: `session.token`, `account.password`/`accessToken`/`refreshToken`/`idToken`, `verification.value`, `passkey.publicKey`/`credentialID`, `apikey.key`.
- `session`, `account`, `verification`, `passkey` and `apikey` rows cannot be inserted or edited. The one exception is deleting a `session` row by primary key, which revokes that session.
- `user`, `email_invite`, `app_collaborator` and `collaborator_invite` rows can be added, edited and deleted — except `user.role`, `user.banned`, `user.banReason`, `user.banExpires` and `user.status` (change roles, bans and approvals in the Users tab). You can edit your own `user` row (e.g. clear `onboardedAt` to see the tour again) but not delete it, so an admin cannot lock themselves out.
- Everything else is read-only by default, including tables a later release adds, so new auth state can never become silently writable.
- The browser is unavailable while impersonating, and every read and write re-checks the admin gate and this policy server-side.
