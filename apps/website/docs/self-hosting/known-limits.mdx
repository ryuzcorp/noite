Noite is alpha and self-hosted: you run it, so you decide who gets an account. These are the gaps that matter for that decision. Each one is on the roadmap; none is a surprise to the maintainers. To report a vulnerability, see the [security policy](https://github.com/ryuzcorp/noite/blob/main/SECURITY.md).

## Tenant isolation

Under `NOITE_TENANCY=multi` ([Tenancy](/self-hosting/tenancy)) tenant code runs as unprivileged users, with a cleared environment and an egress policy. Builds and release commands run as **one uid per app**, so two concurrent builds cannot read each other's worktrees or caches. That is still a sandbox for **semi-trusted** tenants, not for adversaries:

- **Bucket keys in fleets.** A fleet's celld process holds scoped keys for its own prefix only — except on stores with no prefix-scoped keys (R2) or without the extra `NOITE_CREDENTIAL_PROVIDER=aws` configuration (AWS S3), where fleets keep the object store's **root** keys as an explicit `root` mode the boot log, `/ready` and `make doctor` all name.
- **Object store reachable from Worker code and builds.** The store's unauthenticated surface (it answers 401/403) is the one private address tenants may reach, because celld and the release command's scoped key need it. Builds hold no keys.
- **Per-app memory caps.** Each tenant fleet runs in its own cgroup with its own `memory.max` (`RUNNER_FLEET_MEMORY_MB`, overridable per app in Settings → Limits), so one app's growth hits its own limit instead of pushing every app toward the same shed threshold. Swap is disabled per leaf, so a capped fleet is OOM-killed rather than swapped out; a host `/noite.swap` (created by the installer under 4 GB) is a safety net for the resident services, not a fleet budget. An OOM kill restarts the fleet and records a tenant-visible `fleet` event and fleet log line. It needs the multi-only cgroup grant (`docker/compose.multi.yaml`); without it fleets share the container cgroup and `multi` stays at 503.
- **A build has its own capped cgroup.** Install, build and release steps run in a `build` leaf with `memory.max` (`RUNNER_BUILD_MEMORY_MB`; unset derives the detected memory minus a 1 GiB resident floor, split across build slots, clamped 512–4096 MiB), a bounded `memory.swap.max` (`RUNNER_BUILD_SWAP_MB`; unset derives the host's swap across the build slots), `memory.oom.group`, a hard `cpu.max` of one core less than the box split across the build slots, and a low `cpu.weight`/`io.weight`. The RAM cap keeps the runner, fleets and Caddy resident; a build larger than the box's spare RAM swaps the overflow, so the ~1.3–1.5 GiB Vite 8/Rolldown build of a Void app completes on a small box (slowly) instead of dying at the cap. A step that fills RAM and swap is killed alone — the others keep serving — and the deploy log names both budgets. Fleet leaves keep zero swap, so a capped fleet still dies rather than swapping the host to death.
- **No container per build.** Depth is uid, environment, resource limits and egress rules. Rootless containers or gVisor are not planned unless tenants are expected to be hostile.
- **Void Sandboxes (`void/sandbox`) run through a platform controller.** An app using them gets a runner-owned `noite-void-sandbox` script cohosted in its fleet ([Void sandboxes](/self-hosting/operations#void-sandboxes)): one fleet's sandboxes are unreachable from any other fleet or the public internet, and previews get their own controller. Each fleet admits at most `NOITE_VOID_SANDBOX_MAX_CONCURRENT` live sandboxes (default `4`), and aborting an exec's signal sends SIGKILL to the process, as on Workers. Custom sandbox images must carry the sandbox shim (`/usr/local/bin/sandbox-shim`) — base them on a shim-carrying image or file operations fail at container start.
- **Sandbox containers share the host kernel.** Apps on the agent template run tools in celld `containers` classes on the install's engine. Only the runner holds the host engine socket — each fleet gets a filtered per-fleet socket, cross-app sandbox dials are refused, and deploys may only reference registry images or Dockerfiles that run nothing (no `RUN`, base images vetted for `ONBUILD` and pinned by digest; no per-class runtime). But the containers run under runc, which shares the host kernel; gVisor support for Sandbox containers is on the roadmap. Pulled images are never garbage-collected either, so engine disk grows with every new image. `NOITE_SANDBOX=0` turns the whole plane off ([Tenancy](/self-hosting/tenancy#sandbox-containers)).
- **Workers `caches` is per-fleet, in memory.** `caches.default` is shared by every script of the fleet's deployment (`CELLD_CACHE_SCOPE=deployment`), like a Cloudflare zone, and lives in the fleet process's memory (64 MiB default cap), not on an edge network. Noite fleets are single-node, so entries are coherent per fleet; Void ISR serves L1 from `caches.default` with KV behind it, and `revalidate()` purges both.

The remaining gaps are tracked here: [Noite roadmap board](https://github.com/orgs/ryuzcorp/projects/1) (the "harden multi-tenant mode" item is still a draft).

If a tenant is not someone you would give shell access to a shared server, do not give them a push key yet.

## Custom domains

A hostname is reserved on first claim, and Noite does not check DNS or ownership: **a tenant can claim a hostname they do not own**, and the first claimant wins. The certificate is issued on demand on the first visit. Treat custom domains as an admin-trusted feature until a DNS/TXT check ships.

## Platforms

- **Railway** does not grant `NET_ADMIN`, so the egress policy cannot run there: use `NOITE_TENANCY=single` and invite nobody to push code ([Platforms](/self-hosting/platforms)).
- **Coolify** passes TLS through to Noite, so [per-visitor rate limits](/self-hosting/protection) are off; per-app ceilings still work.

## Operations

- **Moving to a new alpha is a fresh install.** Alpha builds do not migrate data between versions: `install.sh` refuses an existing install, and the runner and control D1 refuse a database written by another alpha. A version move means uninstalling (which deletes the volumes) and installing again; every tenant fleet cold-boots with the runner. The window is short: measured on a 32-core host with 1, 5 and 15 apps, every app was serving again within 5.1 s of the container starting (the fastest fleet in ~2.1 s), because the runner starts every fleet before it deploys the control UI and the fleets boot in parallel. The edge holds a visitor's request for up to 20 s ([Operations](/self-hosting/operations#updating)).
- **One alpha cannot read another alpha's data.** The runner and control databases carry a schema stamp; an image from a different alpha refuses it instead of reshaping it. Move versions by uninstalling and installing fresh, after a [backup](/self-hosting/operations#backups) if you need the data.
- **Snapshot loss window.** The runner's SQLite is snapshotted to the bucket within about 22 s of changes settling, so a lost volume loses at most that much recent state, as long as uploads succeed. While uploads fail (store unreachable, credentials refused), every change since the last successful upload is at risk. `/ready` and `make doctor` report the seconds since the last upload and the last upload error, so watch those.
- **Telemetry recovery is bounded by retention.** Metrics, logs and errors are rebuilt from bucket Parquet: a failed ingest pass now holds its watermark and catches up hour by hour, and a window can be replayed by hand. Nothing older than `RUNNER_TELEMETRY_RETENTION_DAYS` (30 days by default) can be recovered — celld has pruned it ([Telemetry](/self-hosting/storage#replaying-a-window)).
- **One node.** The control UI and the runner restart together and nothing fails over; availability is that of the one container and its bucket.
- **RustFS is not a qualified store.** It is the zero-config default and passes celld's startup check, but for production use one celld qualifies: S3, R2, GCS, Tigris or Azure Blob ([Storage](/self-hosting/storage)).
