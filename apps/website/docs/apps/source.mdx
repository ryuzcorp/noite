The **Code** item under an app in the sidebar opens `/apps/<id>/source`; the **App** item beside it goes back to the app's overview. Everything there reads the push mirror, which holds every pushed branch — not only the deployed one.

## Layout

Code mode has one bar: the branch picker on the left, **History** and **Changes** on the right. The files take the page, and every pane is resizable: the divider between the file tree and the editor, the one between the editor and the side panel, and the one above the [Terminal](#terminal). Drag one, or focus it and step it with ← / → (↑ / ↓ for the terminal, `Home` / `End` to take a pane to its own limit), and each split is kept in this browser — a reload, a branch switch or a reopened panel opens where you left it. Each pane keeps its own share of what the others leave. Each button opens a side panel on the right, an even share of what the file tree leaves to begin with, and opening and closing it slides the panel (and the editor beside it) into place. On narrow screens the panel covers the files instead. One panel holds both tabs, and switching between them keeps what each one holds: the commit form keeps the message and target you were typing, and History stays on its page. Click the active button again, or the panel's close button, to hide the panel: every tab in it is let go. The open panel is in the URL as `?panel=history` or `?panel=changes`, so refresh and deep links keep it. The pages below it (a commit, a compare) carry a link back to the files in place of the picker, returning to the ref and the open file you came from. Pull requests have their own pages; see [Pull requests](/apps/pull-requests).

## Branch picker

Code mode opens on the default branch (`main`), where browser edits are committed by default. The branch picker is a dropdown that lists every branch. Once the app has deployed, the first entry is the commit production is serving, by its short SHA under a **Production deploy** badge (read-only), to browse exactly what is running. The default branch carries a **default** badge in the same spot. Each other branch shows how far it is ahead of or behind `main`, and has a **Compare** link. Admins also get a **Delete** button, except on the default branch; deleting the branch you are browsing returns to the default branch, and deleting any branch also deletes its preview environment and that environment's own data, and leaves any open pull request from it without a head. The URL carries the browsed ref as `?ref=` (absent for the default branch) and the open file as `?file=`, so a link to a file on a branch is shareable. Any tag or commit works in `?ref=` too.

At the bottom of the dropdown, **Create** makes a branch from the ref you are browsing and switches to it. This needs the `push` role. A create or delete publishes exactly like a push: the tip bundle and manifest are written, and `main` moving deploys.

Browsing a tag or a raw commit sha (both work in `?ref=`) is read-only. Any branch opens editable while you have the `push` role, and a commit lands on the branch you are reading ([below](#browser-edits)).

## Files and diffs

The tree lists the ref's files with sizes; clicking one opens it in the editor. Binary files are detected and not rendered, blobs are capped at 256 KB, and a diff is capped at 1 MB. On a branch you can edit, the tree marks every file you have added, changed or deleted but not pushed yet, and the folders that hold them. The editor's own header shows the open file's change the same way — the same letter (added, modified, moved, deleted) beside its name — from the same unpushed changes, so it stays right across a reload and follows a discard, an undo or another tab's write.

The tree also reads the checkout's own `.gitignore` — the root's and one in any folder under it, with git's rules (`!` negation, a trailing `/` for folders only, an anchored `/`, `**`, comments, escapes) — and paints what it excludes **dimmed**, the way an editor does. That is how the output of a Terminal build ends up visible where git would not list it at all: `dist`, `out`, `.wrangler`, `.ilha`, an installed `node_modules`. An ignored path is not part of the checkout: it never appears in **Changes** and no push carries it, exactly as git leaves it out. A folder the rules exclude is shown as the folder alone, dimmed — nothing under it is read, because git does not look inside it either, and `node_modules` alone is large enough to make that the only sane thing to do. A path the commit already holds is never dimmed: git keeps tracking what it has committed, so a file under an ignored folder that is part of the commit stays a row and stays a change. The rules apply as soon as they are written: add `build` to `.gitignore` in the editor or straight from the Terminal and its row goes dim on its own.

## Shortcuts

- **Cmd/Ctrl+F** opens find in the open file, and **Cmd/Ctrl+Alt+F** adds replace. Both are the editor's own panel, not the browser's.
- **Cmd/Ctrl+click** a symbol to jump to its definition ([Code intelligence](#code-intelligence)).
- **F2** on the selected row renames it, and **Delete** or **Cmd/Ctrl+Backspace** deletes the selected rows after the confirmation ([Browser edits](#browser-edits)).
- **Ctrl+C** at the terminal prompt interrupts the foreground job ([Terminal](#terminal)).

## Repository limits

Code mode checks out the whole ref in the browser, so the runner caps a checkout at **5000 files** and **100 MiB**. A repository over either cap is refused with `413 repository too large for Code mode: …` instead of opening. Shrink the ref (or move large assets out of the repository) to bring Code mode back.

## Code intelligence

TypeScript and JavaScript files get the editor help you would expect, computed in a web worker from the ref you are browsing:

- **Diagnostics** appear as inline markers on the offending token. They re-check a moment after you stop typing, using the repository's own `tsconfig.json` (ESNext / `bundler` / `react-jsx` defaults when it has none).
- **Hover** a symbol for its type and JSDoc. The tip opens once the pointer has rested on the symbol for 0.3 s and highlights the type like the editor does. On a marked token, the tip lists the diagnostic below the type.
- **Cmd/Ctrl+click** a symbol to jump to its definition, opening the other file at that line. A definition that lives in a package, or in TypeScript's own libs, has no row in the tree, so its declaration is shown right where you clicked instead.
- **Inline prediction** offers the completion TypeScript ranks highest at the cursor, as ghost text.

Imports are resolved package by package, from declarations fetched for the exact versions the repository's lockfile pins. The language service's worker reads the bare imports **the open file's program needs** — that file's own imports, those of the repository files it reaches, plus `tsconfig.json`'s `types`, the JSX runtime a `.tsx` file needs, and your drafts; nothing else in the repo is fetched for, so opening `cloudflare.config.ts` does not drag in Vite's or wrangler's graphs. It takes each package's version from `bun.lock`, `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock` — falling back to the range in `package.json` — and fetches that package's declarations from [esm.sh](https://esm.sh). Following the files' own imports, it fetches theirs too. The fetched files are cached in the browser and so are the misses — a package esm.sh does not serve is not asked for again for seven days, a build failure for an hour — so reopening the editor or switching branches is instant, and the language service is never fed two versions of one package. A package whose declarations cannot be fetched — offline, blocked, private or not built — simply stays unresolved and reads as a missing module, so a browser with no network gets no package types.

Read-only refs (a tag, a raw commit sha, or a branch you may not push to) keep hover and Cmd/Ctrl+click, and never predict. They also show no markers: markers live inside an edit session, and a read-only ref deliberately has none.

## History and commits

The **History** panel lists the browsed ref's commits newest first: subject, author, time and short SHA. **Newer** and **Older** page through them (`?skip=`), and are hidden while everything fits on one page. With a file open, **Only `<file>`** narrows the list to that file. A commit opens at `/apps/<id>/source/commit/<sha>`, with its metadata and parents, the changed files with additions and deletions (binary files flagged), and the patch against its first parent; the link back to the files returns to the ref and the open file you opened it from, and a parent link carries them onward.

## Compare

The compare page (`/apps/<id>/source/compare?base=&head=&ref=`) shows two refs: their commits, the three-dot diff, and whether a squash merge would apply cleanly. Open it from a branch's **Compare** link in the picker, or directly (`ref` is the branch you were browsing, so the link back returns to it). The **Open pull request** button starts one from the pair you are looking at ([Pull requests](/apps/pull-requests)).

## Browser edits

Opening a file and changing it stages a web commit. You can edit as many files as you like: each keeps its draft while you open others. The **Changes** button shows how many files you have changed.

Right-click in the tree for **New File**, **New Folder** and **Delete**. On a folder they act inside it, on a file in its folder, and on the empty space below the files at the root. A new file is named in place and opens empty in the editor. Delete asks first; on a folder it removes every file in it. Ctrl/Cmd-click selects several rows: right-click one of them and **Delete (N)** removes them all after one confirmation. Git can't store an empty folder, so a new folder lives only in your browser until it holds a file. On a read-only ref the tree has no menu: right-clicking says the checkout is read-only.

Drag a file or folder (or a whole selection) onto a folder to move it there. Dropping onto a file moves into that file's folder, which is how you move something back to the root: drop it on a top-level file. A move onto a name that already exists is refused. The open file follows its move, edits included. Moves don't read file contents, so binary and large files move too.

**Rename** (in the menu, or F2 on the selected row) edits the name in place; it is a move, so the same rules apply. **Delete** or Cmd/Ctrl+Backspace on the selected rows asks, then deletes them.

**Upload files…** in the menu, or dropping files and folders from your computer onto the tree, adds them where you dropped: in a folder, next to a file, or at the root for the empty space. Text files (UTF-8, up to 256 KB) become drafts you can edit; anything else is a binary file shown by its size. A push holds up to 100 files and 25 MB, and each upload up to 10 MB. Uploading onto a path that already exists asks whether to replace it.

The **Changes** panel shows every draft as a diff against the file as it was, and lists moved files (`old → new`) and deleted files, each with a **Restore** button. Paths the `.gitignore` excludes are never in it — they are the tree's dimmed rows ([Files and diffs](#files-and-diffs)). **Discard** on a change throws it away (an edit goes back to the committed text, an added file leaves the tree); **Discard all** resets everything. Both ask first. Its form at the bottom takes a commit message (left empty, it is built from the changes — `Add README.md` for one file, `Update 3 files` when they are mixed) and where to commit — a select of the app's branches, the one you are browsing first, then the default branch, then the rest newest-first:

- **A branch**, listed by name, which is where the commit lands: `main` deploys the app and wakes it if it was sleeping, and any other branch with an environment redeploys that environment.
- **New branch…**, with a name. The branch starts at the tip of the branch you are browsing, which stays as it was, so the open file goes back to its old text. The panel then links to a pull request into the branch you were browsing — as it does for any commit that created a branch.

**Push** sends every draft, upload, move and deletion as one commit, with a validated set of paths. Then the panel says where it landed. If the push fails, the drafts and the form are kept, so you can retry.

Unpushed changes live in this browser, per app and branch. A reload, a visit to another page, or closing and reopening the tab doesn't lose them, and they stay until you **Push** or **Discard all** — nothing expires. Tabs open on the same branch share them: an edit, upload, rename or discard in one tab shows up in the others as you make it, and every tab can edit. If two tabs change the same file at once, the last write wins; when a peer's write lands on a file you still have unsaved edits to, the panel says `<path> was changed in another tab`, and you can dismiss the notice. If the branch moved in the meantime, the panel says the changes are based on an older commit, and the push may conflict. Editing, uploading and discarding only ever touch your browser's copy of the checkout; nothing reaches the server until you push.

- **Any branch can be edited** while you have the `push` role, and each keeps its own unpushed changes. A tag, a raw commit sha, or a branch you may not push to stays read-only: the Changes panel says why and what to do, and hides the commit form, so switch to a branch you can push to edit.
- **Empty repositories work**, so you can seed a blank app from the browser.
- When a branch is **protected** — `require_pr` on, you are not an app admin, and it is the default branch — its entry in the target select is greyed out and only **New branch…** pushes ([Branch protection](/apps/pull-requests#branch-protection)).

Every commit Noite writes — browser edits, merges, template imports — is authored and committed as `<your name> <your user id>@users.noreply.<domain>`, never your email.

## Preview

Previews are deployments. A branch with an environment deploys every push to its own `<label>.<slug>.<base>` host on celld, from the same build pipeline as production and with its own storage; the app's environments are listed on [Environments](/apps/environments). Nothing runs inside your browser and nothing runs on the control UI's origin.

The workspace itself — the file tree, the editor and the [Terminal](#terminal) — still runs in the browser pod, in a document on the app's own `app-0.preview.<slug>.<base>` host rather than the control UI's origin: that document creates the workers that run an install and its lifecycle scripts, and anything you type into the Terminal, while the control UI keeps the editor, the file tree and every signed-in call, and only talks to it. None of the pod's code shares the control UI's cookies, API or storage, and your unpushed changes are saved under that host, out of the control UI's reach and out of any other app's. If the app's pod host cannot be read, the workspace does not open at all (Code mode says why) rather than running its code on the control UI's origin.

The panel frames what is deployed for the branch you are browsing, and it follows your edits: while the workspace has uncommitted changes it frames your own **workspace preview** — a hidden ref, `refs/previews/<user>/<branch>`, that no branch list, pull request or clone ever shows — otherwise the branch's own environment (production for the default branch). A branch without any environment says so, and offers **Deploy preview** with the link to the **Deployments** tab, where you create the branch's environment. **Deploy preview** snapshots the uncommitted changes and deploys them to that workspace preview, without pushing the branch and without touching your changes; once a preview exists the button reads **Redeploy**, and a preview whose snapshot is older than the latest edit says so above the frame, with the deploy right there. A push is still what redeploys a branch environment, and the frame reloads once that deploy succeeds — while it builds, the previous build keeps serving and the frame is left alone. The panel's single bar holds the target's status dot and name (with the workspace preview's remaining life), **Branch**/**My preview** when a branch has both, the deploy button — off, with the reason in its tooltip, while there is nothing to deploy, the checkout is read-only or a deploy is running — the address — edit it and press Enter to load another path or URL in the frame (Escape puts it back; an empty field is a no-op) — reload, copy the address, open in a new tab, the target's deploys on the **Deployments** tab, and close. The latest deploy's build log sits under the frame in a disclosure that is open while the deploy is still going and closed once it has succeeded, so the frame keeps the height; a frame that has not loaded after 20 seconds says so and can be retried, and an environment that failed or is stopped says that instead of a blank page. If a members-only environment cannot hand the frame a grant, the frame shows the reason on its own small page (`/api/env-auth`): this preview expired or was deleted, you do not have access to this environment, the runner did not answer, or — signed out inside a frame — a sign-in link that opens top-level instead of the login form.

## Terminal

**Terminal**, at the bottom of the file tree, opens a shell under the editor (and the right panel), in the URL as `?terminal=1`, with its own divider above it: drag it (or use ↑ / ↓ on it) to give the shell more or less room, and the split is kept in this browser. It runs in the same browser pod as the editor, at the checkout's root (`/home/project`), so it sees exactly the files you are editing: a file it creates, changes or removes shows up in the tree, the editor and the Changes panel right away, and is pushed like any other change — unless the checkout's `.gitignore` excludes it, in which case it shows up dimmed and is not a change at all ([Files and diffs](#files-and-diffs)). Nothing runs on the server.

Anything you run here — `npm install`, `npm run dev`, a build — happens in that pod, on the app's own `app-0.preview.<slug>.<base>` host: its output streams into the terminal and **Ctrl+C** interrupts it. Closing the terminal keeps the shell and its scrollback for when you open it again. The terminal is drawn by [ghostty-web](https://github.com/coder/ghostty-web).
