title: Deployment
description: Deploy Noite anywhere with Docker Compose — one image, bundled RustFS or your own S3 bucket.
---

Noite ships as **one image**, `ghcr.io/<owner>/noite`. Its runner is PID 1 and supervises everything else in the container: Caddy (the edge), the control UI (a celld node, fleet #0, bundle baked into the image) and one celld fleet per tenant app. `docker/compose.yaml` runs it next to the bundled RustFS store; `docker compose up -d` is the whole install, and no host-side build or deploy step exists.

|  | A: bundled RustFS | B: your own bucket |
| --- | --- | --- |
| Start | `make up-prod` (or `docker compose -f docker/compose.yaml up -d`) | the same, plus `--scale rustfs=0` and `S3_ENDPOINT` + keys in env |
| S3 | RustFS container (`:9000`, loopback-published) | R2, Tigris, S3 (celld-qualified), or anything SigV4 |

`docker/compose.yaml` pulls the image and gives every variable a default, so it also boots as-is on a cloud VM or from a Compose store/panel (Arcane, Portainer, Dockge, …) and serves the control UI on `http://localhost:9080`. A checkout builds instead with `make up` (`docker/compose.build.yaml`).

## Prerequisites

- A Docker or Podman host with Compose.
- DNS: `app.<domain>` (control UI), `api.<domain>`, `git.<domain>`, plus `*.<domain>` for tenant apps. The apex stays free for your marketing site.
- Ports 80/443 reachable — Caddy terminates per-host TLS itself via on-demand certificates (ask-gated, so only live hosts get certs).

## A: bundled RustFS

```bash
cp .env.example .env
# edit .env: production values (see below)
make up-prod && make logs      # `make up` builds the image from the tree instead
```

Production `.env` essentials:

```bash
BASE_DOMAIN=noite.now
CONTROL_SUBDOMAIN=app
BETTER_AUTH_URL=https://app.noite.now
GIT_PUBLIC_BASE=https://git.noite.now
RUNNER_TOKEN=<long-random>            # shared runner↔ui bearer token
BETTER_AUTH_SECRET=<long-random>      # session signing secret
RUSTFS_ACCESS_KEY=<key>               # default dev values must change
RUSTFS_SECRET_KEY=<secret>
NOITE_IMAGE=ghcr.io/<owner>/noite:<sha>   # pin a release
```

`CONTROL_SUBDOMAIN` empty means the control UI is served on the bare domain (the dev default); `app` is the production setting. Set `BETTER_AUTH_URL` to the final URL **before** users register — passkeys are bound to it. Open `https://app.noite.now`, create the owner account (first signup), then deploy: `cd apps/noite/test && ./deploy.sh`.

Other variables worth setting: `HTTP_PORT` (default 9080) / `HTTPS_PORT` (9443), `NOITE_S3_BUCKET`, `NOITE_ADMIN_EMAIL`, `NOITE_EMAIL_WEBHOOK_URL`, `NOITE_SMTP_FROM`, `CONTROL_EXTRA_HOSTS` (extra hostnames serving the control UI), `CADDY_AUTO_HTTPS`, `NOITE_TENANCY` (see [Tenancy](#tenancy)).

## B: your own bucket

```bash
S3_ENDPOINT=https://s3.us-east-1.amazonaws.com \
AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... \
NOITE_S3_BUCKET=noite S3_PUBLIC_ENDPOINT=https://s3.us-east-1.amazonaws.com \
docker compose -f docker/compose.yaml up -d --scale rustfs=0
```

Key requirements: Get/Put/Delete/List on the bucket. The bucket is created if the key allows, otherwise create it first. Same production `.env` as option A, minus the `RUSTFS_*` keys.

## Storage backend

celld qualifies Amazon S3, Cloudflare R2, Google Cloud Storage, Tigris and Azure Blob Storage; the store must provide conditional writes, read-after-write consistency and ranged reads. celld runs a storage-contract check at node startup — a contract violation stops startup, an ambiguous transport error warns — so a store that fails the contract stops loudly instead of corrupting state later. MinIO community edition passes celld's storage test but is not qualified for production.

Noite's bundled default is RustFS, which is **not** on celld's qualified list. celld's own startup check still runs and passes on it, and every node boots normally, but for production the recommended path is your own bucket on a qualified store. Bundled RustFS stays the zero-config default for trying Noite out and for single-host installs.

## Tenancy

`NOITE_TENANCY` decides whether other people may push code to the install. Unset, it is `multi` off `localhost` and `single` on `localhost`.

- **`multi`**: tenant builds and release commands run as the unprivileged `build` user with a cleared environment (no platform secret reaches them), tenant fleets as the `fleet` user, and an nftables policy on those users closes new connections to loopback, private ranges and cloud metadata. The one private address allowed is the object store the fleet's own celld needs; Worker code can reach it but holds no keys. `/data` is private to the runner. Release commands are skipped until scoped per-app bucket keys exist (SPEC, Scoped credentials). All of this needs `NET_ADMIN`, `SETUID`, `SETGID` and `CHOWN`, which `docker/compose.yaml` grants; without them the runner keeps `/ready` at 503 with the reason and refuses builds.
- **`single`**: only you push code. No egress policy, and release commands run with the root bucket keys.

`make e2e-isolation` proves the `multi` claims: a hostile tenant app tries to read platform secrets and files and to reach every internal API from its build, its release command and its Worker, and the lane asserts every attempt fails while internet egress still works.

## Verify

```bash
curl https://api.<domain>/health                    # edge → runner
curl -s https://api.<domain>/v1/apps -H "Authorization: Bearer $RUNNER_TOKEN"
make doctor                                         # /ready, API auth, the edge, control auth, celld control node
```

`/ready` is the summary: 200 only when the first reconcile ran, the bucket answers, isolation holds (in `multi`), the control fleet is healthy and Caddy accepted its config, and its body names whatever is failing; it is also the container's healthcheck. `make doctor` prints it and adds celld's two documented operator surfaces for the control node: `GET /.well-known/celld/health` (the public boolean) and `celld diagnose --read-only` (node leases, peer probes, advertised addresses).

Push the sample app via `apps/noite/test/deploy.sh` (point its remote at `https://git.<domain>/<slug>`) and open `https://<slug>.<domain>`.

## Invitations

Registration is invite-only once the instance is bootstrapped. The **first** account to sign up needs no code and is promoted to the `admin` role, so god-mode works without `NOITE_ADMIN_EMAIL`; every later registration must present a single-use invitation code. Each new account receives `INVITES_PER_USER = 2` codes of its own, so an invitee can pass one on without admin rights.

Codes are 12 characters in four-char groups (`ABCD-EFGH-JKLM`) drawn from an unambiguous alphabet, and a code that is used, revoked or unknown is refused with a specific message before any account is created. Redemption is a single atomic claim (`UPDATE ... WHERE usedBy IS NULL`), so one code admits exactly one account even under concurrent signups.

- Members read their unused codes in the "Invitations" card on `/account`.
- Admins mint 1–50 more and revoke unused ones from the Invitations panel in `/god-mode`.
- The signup form shows the code field only when `GET /api/invite/status` reports the instance is past its first account, so the bootstrap account never sees it.

## Custom domains

Beyond the automatic `{slug}.<domain>` subdomain, each app can hold extra hostnames. They live in the runner's `app_domain` table, keyed by hostname (primary key — one app per hostname) and driven by `GET/POST /v1/apps/{id}/domains`, `DELETE /v1/apps/{id}/domains/{hostname}` (and the same three as RPC `domains.list|add|remove`); the app settings UI exposes add/remove/list.

Validation is `lifecycle.rs::hostname_ok` — lowercase DNS shape, at least two labels, no wildcard, IP literal, port or path — and the API additionally refuses platform hostnames (the base domain and its subdomains, plus anything in `CONTROL_EXTRA_HOSTS`). Adding a hostname another app already holds returns 409.

Routing follows the app's state: the runner's Caddyfile writer gives a registered hostname a site pointing at the app's port only while the app is deployed and running, and the on-demand TLS gate (`/v1/edge/tls-ask`) mints a certificate only for a hostname that exists _and_ whose app is live. The wildcard fallback page also resolves custom hosts, so a not-yet-deployed name lands on Noite instead of a bare 404.

Operator steps: add the hostname in the app settings, point its DNS at the server, and open it — TLS issues on the first visit. No DNS/TXT control check exists yet; `SPEC.md` records it as later hardening.

## Limits

One host runs many fleets in one container, so these bound what the fleets can take together:

| Setting | Default | Effect |
| --- | --- | --- |
| `RUNNER_MAX_APPS_PER_USER` | `10` | Per-account app quota, enforced in the runner on `apps.create` — an API key cannot bypass it. |
| `RUNNER_FLEET_MAX_RSS_MB` | `0` (celld's default: 80% of the container's memory) | Passed to each fleet as celld's `CELLD_MAX_RSS_MB`: when the container's memory passes it, fleets shed cells (503 + `Retry-After`) instead of the container OOM-ing. celld measures the container's cgroup, which every fleet shares, so this is a container-wide threshold: a small per-app value like 512 closes every fleet as soon as the container as a whole uses that much. |
| `RUNNER_FLEET_IDLE_EVICT_S` | `300` | Passed as `CELLD_IDLE_EVICT_S`: idle cells hibernate and hand their memory back. |
| `RUNNER_FLEET_LOG` | `error,celld=warn` | The fleet's own `RUST_LOG`, so celld's runtime warnings and errors reach the per-app log view (the runner's own filter used to suppress them entirely). |

The celld-side variables are documented at [celld.dev/docs](https://celld.dev/docs/) (environment variables). `RUNNER_MAX_APPS_PER_USER` is Noite's own knob.

Rate limiting is built in, in two layers. Better-auth budgets per client for `/api/auth/*` (`NOITE_AUTH_RATE_LIMIT`, default 600/min, with `advanced.ipAddress.ipAddressHeaders` set so the proxy's client address — not the proxy itself — is the bucket key), and a platform limiter in the worker (`NOITE_RATE_LIMIT_RPM`, default 600/min **per route class** — `auth`, `invite`) answers 429 + `Retry-After` before the request reaches better-auth or D1. `0` disables either. Behind the edge each request carries its real client address; in the raw-port e2e lane there is no proxy, so every request shares one bucket and the lane raises both budgets.

## Telemetry

Tenant fleets run `CELLD_OTEL=1` with celld's bucket sink: Parquet under `telemetry/traces/` and `telemetry/logs/` in the fleet bucket, no collector service. The flush is `CELLD_OTEL_FLUSH_MS=5000` (the docs' near-live value) and retention is `CELLD_OTEL_RETENTION=14d`, matching the runner's `app_metric` prune.

A short flush requires a compaction job — the docs are explicit that queries grow slow within hours otherwise, and that celld does not compact its own files. The runner runs it hourly via `metrics::compact_fleet`: for the hour that just ended, per node directory, one DuckDB `COPY (...) TO .../compacted.parquet (FORMAT parquet, COMPRESSION zstd)` ordered by `start_unix_us`, then the source files are deleted. Deletion happens only after `head-object` proves the compacted file exists, so a failed copy can never lose spans; `union_by_name=true` merges an hour that spans a schema change (the docs call the schema `v0-unstable`). The current hour is never compacted.

Runner queries are day-scoped: the aggregation window stops 10 s behind the flush and names only the day directories it spans — the docs' "a query that reads one day therefore touches only that day's files" — instead of globbing the whole retention.

To read the same data yourself, point DuckDB at the fleet bucket the way the runner does (the `SET s3_endpoint/s3_region/s3_access_key_id/s3_secret_access_key/s3_url_style='path'` preamble in `apps/runner/src/host/metrics.rs`) and aggregate the hourly Parquet under `s3://<bucket>/fleets/<slug>/telemetry/traces/<node>/<yyyy>/<mm>/<dd>/<hh>/*.parquet`; `celld.fetch` spans count as requests, `ok` is the error flag, `duration_us`/`queue_wait_us` the latency and queue wait.

## Coolify

Point a Docker Compose resource at `docker/compose.yaml` (repo root, branch `main`): the same file as `make up-prod`, driven by env. In Environment Variables, set `BASE_DOMAIN` to your domain (defaults to `localhost`) and `BETTER_AUTH_URL` / `GIT_PUBLIC_BASE` to match, the secrets (`BETTER_AUTH_SECRET`, `RUNNER_TOKEN`, and `RUSTFS_ACCESS_KEY` + `RUSTFS_SECRET_KEY` or your own bucket's keys) and `NOITE_IMAGE` pinned to a SHA tag. Nothing auto-generates secrets; dev defaults are refused on real domains. Deploy, then paste the real hostnames once on the `noite` service's Domains field: `https://app.<domain>:80,https://api.<domain>:80,https://git.<domain>:80`. The apex stays on your marketing site. Behind a terminating proxy set `CADDY_AUTO_HTTPS=off` (Noite's Caddy still mints per-host certs on demand there).

### Downtime model

Coolify does not do rolling updates for Compose: `docker compose up` stops a service before starting its replacement. A new image restarts the runner and every tenant fleet with it (they cold-boot, roughly a minute for many apps), so batch upgrades, deploy them off-peak, and pin `NOITE_IMAGE` to a SHA tag.

Tenant subdomains (`<slug>.<domain>`) are fully automatic: no per-app steps, no wildcard cert, no DNS provider. A Traefik TCP router forwards every `*.<domain>` SNI straight to Noite's Caddy on `:443`, which mints a per-slug certificate on demand (ask-gated by the runner at `/v1/edge/tls-ask`, so only live tenant and platform hosts get certs).

One-time setup (besides `*.<domain>` DNS pointing at the server): save this file under `Servers > server > Proxy > Dynamic Configurations` in Coolify. It is static text that Coolify cannot mangle, and `noite-tenants@docker` resolves the TCP service the `noite` service label defines:

```yaml
tcp:
  routers:
    noite-tenants:
      entryPoints: [https]
      rule: 'HostSNIRegexp(`^.+\.<domain>$`)'
      service: noite-tenants@docker
      tls: { passthrough: true }
```

Then redeploy once and confirm the `noite-tenants` router in the Traefik dashboard. The first visit to a new slug pauses a few seconds for certificate issuance; certs persist in the `noite-data` volume. If passthrough misbehaves, the fallback is `https://<slug>.<domain>:80` per app (exact hostnames use the plain HTTP challenge).

## Railway

One service from the image, one volume, one bucket:

| Service | Image | Volume | Public domain |
| --- | --- | --- | --- |
| `noite` | `ghcr.io/<owner>/noite:<sha>` | `/data` | `*.<domain>` → port `80` |
| `rustfs` (or use R2/Tigris) | `rustfs/rustfs:1.0.0` | `/data` | none |

`noite` takes the same variables as a Compose install: `BASE_DOMAIN`, `CONTROL_SUBDOMAIN=app`, `BETTER_AUTH_URL=https://app.<domain>` (set before the first registration: passkeys bind to it), `GIT_PUBLIC_BASE=https://git.<domain>`, `BETTER_AUTH_SECRET`, `RUNNER_TOKEN`, the bucket (`S3_ENDPOINT=http://rustfs.railway.internal:9000` and its keys, or your R2/Tigris endpoint), plus `CADDY_AUTO_HTTPS=off` (Railway terminates TLS) and `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=35` so the runner's stop budget fits. For a healthcheck, set `PORT=8080` (Railway probes the port in `PORT`; the runner always listens on 8080 and Caddy on 80, so this changes nothing else), path `/ready`, and `RAILWAY_HEALTHCHECK_TIMEOUT_SEC=600`: a first boot deploys the control bundle and can take minutes.

One wildcard domain is the whole DNS story: add the `*` CNAME, the `_acme-challenge` CNAME and the ownership TXT the dashboard returns for `*.<domain>` on the `noite` service. That covers `app.`, `git.`, `api.` and every `{slug}.` host, because the edge dispatches by Host.

Tenancy: Railway does not grant `NET_ADMIN`, so the egress policy `multi` needs cannot run there. Set `NOITE_TENANCY=single` (otherwise `/ready` stays 503 on the `isolation` gate) and do not invite other people to push code. Railway also wraps the entrypoint, so tini is not PID 1; set `TINI_SUBREAPER=1` so it still reaps orphaned processes.

The volume holds the runner's SQLite, git mirrors, builds and certificates; the runner also snapshots its SQLite into the bucket, so a lost volume restores from there on the next boot. Back up the bucket (Railway volume backups for a RustFS service, provider versioning for R2/Tigris).

## Updating

```bash
docker compose -f docker/compose.yaml pull && docker compose -f docker/compose.yaml up -d
```

The image is disposable and state lives in the volumes and the bucket, so an update is a pull plus a recreate. The runner stops every fleet in parallel inside its stop budget (`NOITE_STOP_BUDGET_MS`, 25 s; Compose's `stop_grace_period` is 35 s), then Caddy, then writes a final state snapshot.

## Data & backups

| Volume | Holds |
| --- | --- |
| `noite-data` | runner SQLite (apps, deploys, env, domains, metrics), git mirrors, builds, fleet working dirs, Caddy config and certificates |
| `rustfs-data` | the bundled bucket: `git/` tip bundles, `fleets/` tenant celld, `control/` UI worker + its D1 (accounts, invites), `runner/state/` runner snapshots |

The runner snapshots its SQLite into the bucket about once a minute after changes (and on every graceful stop), and restores it on boot when the volume has none, so the bucket alone is enough to rebuild an install: mirrors rehydrate from the tip bundles and fleets from their prefixes. `make down` keeps volumes; `make nuke` deletes them (by name too, since podman-compose's `down -v` can skip them) plus local `.wrangler` state. With your own bucket, delete its objects at the provider.

## Backups

```bash
make backup                              # → backups/<UTC stamp>/
make backup DEST=/srv/noite-backups/now  # or anywhere else
make restore FROM=backups/<stamp>        # destructive: replaces the live volumes
```

`make backup` (`docker/backup.sh`) asks the runner for a fresh snapshot (local and bucket), stops the stack for a quiesced copy, tars both volumes into `backups/<UTC stamp>/`, writes a `MANIFEST`, and starts again. Downtime is the tar time. With your own bucket, turn on versioning at the provider instead; the script then covers `noite-data`.

`make restore FROM=...` (`docker/restore.sh`) is destructive and deliberate: it stops the stack, replaces the backed-up volumes, and starts again. Everything written since that backup is gone. Verify with `make doctor`.

Both scripts tar with the Noite image already on the host (`NOITE_BACKUP_IMAGE` overrides).

## Troubleshooting

- **`/ready` answers 503**: its body names the failing gate (`reconcile`, `bucket`, `isolation`, `control`, `caddy`). A fresh install waits for the control bundle's first deploy into `s3://<bucket>/control` (seconds; revision-gated, so a restart with the same bundle and vars skips it).
- **`isolation: …` in multi**: the container lacks a capability or `nft`. Grant `NET_ADMIN`, `SETUID`, `SETGID` and `CHOWN`, or run `NOITE_TENANCY=single`.
- **Boot stops with `runner state restore failed`**: the volume is empty and the bucket did not answer. The runner refuses to start with an empty database (it would overwrite the good snapshot); fix the store and it retries on restart.
- **A deploy fails with `celld deploy does not support these config keys`**: a Wrangler key celld does not accept. Noite strips its own `release` key before deploying; anything else must go.
