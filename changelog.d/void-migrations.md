### Added

- Void apps with D1 migrations now migrate on every deploy: after reload adoption and the health gate, before the deploy is marked success, a `migrate` step collects the pushed tree's `db/migrations/*.sql` (Void's rule: sorted, `seed.sql` excluded) and drives the new Worker's in-worker migration endpoints over the fleet's own listen port with the fleet's `__VOID_PROXY_TOKEN` — protocol v2 where advertised (capabilities negotiated against the tree's dialect, classifier version and list hash, then app migrations with reconcile-on-unknown, then auth migrations), legacy `POST /__void/migrate` for older sqlite runtimes. Execution stays in-worker, so `_void_migrations` and the v2 attempt/lock/fence tables match Void exactly. The log reports `migrate: applied N, skipped M` with the quoted file names; a redeploy skips applied migrations, and a failed migration fails the deploy with `migration <name> failed: <error>`. Prebuilt CLI trees with no `db/migrations` run the worker's bundled migrations without the list-hash check and say so. Each preview migrates its own D1. Non-Void apps deploy exactly as before.
- Postgres/MySQL Void apps are refused loudly at the `migrate` step instead of deploying with an empty database: their in-worker handlers need a Hyperdrive binding Noite does not provide. Move the app to D1 (`database.dialect: "sqlite"` in `void.json`).

### Operator action required

- Migrations are forward-only: rolling back the code never un-applies them, so a deploy that fails at `migrate` leaves applied migrations in place — fix the migration and redeploy, which skips what is already applied. Between reload adoption and the `migrate` step the new Worker briefly serves the old schema (celld adopts the new generation at reload; Void migrates before its traffic switch), so keep migrations backward-compatible. Stopping an app mid-deploy skips its migrations; redeploy to run them.
- Unlike `release`, a failed `migrate` leaves the new Worker serving a half-migrated schema (traffic switched at reload) while the deploy reads Failed. The step is bounded: worker responses past 4 MiB fail the deploy, warning/name lists log the first 20 plus a count, and per-request timeouts cap the worst case at ~11.5 min (~15.5 on the legacy endpoint).
